# 坦克大战 · 代码详解

配合 `main.c` 阅读。源码里已经加了逐段注释，这份文档负责讲**为什么这么写**，
尤其是子弹碰撞那 80 行和局域网联机的协议设计——那是整个程序里最需要动脑子推导的两处。

---

## 0. 先建立整体印象

| 项目 | 数字 |
|---|---|
| 源码 | 约 3900 行（含中文注释），单文件，无第三方库 |
| 窗口 | 客户区 768 × 662（`31×24+24` × `124+22×24+10`），不可缩放；启动时先弹一个模式选择窗口 |
| 地图 | 31 列 × 22 格，每格 24px，**通道 2 格宽**（48px），外圈全是钢墙 |
| 运行期对象 | 2 辆坦克、64 发子弹、4 发追踪弹、10 颗地雷、4 个道具、96 个粒子——**全部是静态数组，零 malloc**；联机的收发缓冲也是静态数组 |
| 联机 | TCP + Winsock2，主机权威同步，固定 60Hz tick，全量快照 |

整个程序只有几张"表"和几件事：

```
几张表：  g_map       地图（哪个格子是什么）
          g_tanks     两辆坦克的状态
          g_bullets   所有在飞的子弹
          g_missiles  追踪弹（瞄准中 / 飞行中）
          g_mines     地雷
          g_items     场上的道具小球
          g_net       联机的 socket、会话号、收发缓冲（见第 9 节）

几件事：  SimulateTick(in, dt)   把状态往前推一个固定 tick（本地/主机共用）
          NetPoll()              联机时非阻塞收发数据、推进握手/大厅状态机
          RenderFrame()          把状态画成像素
          WinMain                每帧先 NetPoll，再按固定 60Hz 累加器驱动上面两个
```

没有对象系统、没有事件回调、没有场景树。所有函数都是"拿全局数据算一下"。
这种写法在几百行的小游戏里是**最优解**：改一个数就能立刻看到效果，不用顺着继承链找。
联机部分也没有引入线程或回调——还是同一个主循环里"每帧轮询一次网络"，
调试时可以单步、断点、printf，和调试本地逻辑没有区别。

## 1. 坐标系：整个程序最容易搞混的地方

游戏里有**两套坐标**，换算只发生在绘制那一层：

```
场地坐标（逻辑）                     屏幕坐标（像素）
原点 = 场地左上角                    原点 = 窗口左上角
     (0,0)                               (0,0)
       +-------- 31×24=744 ------+         +---- HUD 124px ----+
       |                         |         |                   |
  22×24|      坦克/子弹住这里     |   +12px |   (ARENA_X, ARENA_Y)
 =528  |                         |         |        ↓ 场地在这
       +-------------------------+         +-------------------+
```

- 逻辑代码（移动、碰撞、反弹）**只用场地坐标**，从 0 到 744 / 528。
- 只有 `Draw*` 函数里才 `+ ARENA_X`、`+ ARENA_Y` 变成屏幕坐标。
- 地图格子坐标 `(gx, gy)` 和场地坐标的关系是 `px = gx * 24`，
  反算是 `gx = floor(px / 24)`（对负数要小心，所以越界单独判）。

**为什么值得分两套？** 因为场地可以随便挪位置（改 `ARENA_X/ARENA_Y` 就能居中），
而逻辑代码一行都不用动。如果把 HUD 偏移混进碰撞计算，挪一下界面就会全线崩。

## 2. 一帧里到底发生了什么

`WinMain` 每帧按固定顺序做这几件事：

| 顺序 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| 1 | `PeekMessage` 把消息队列抽干 | 不阻塞，抽完就往下走 |
| 2 | 菜单模式？→ `Sleep(10)` 直接跳过本帧 | 玩家还没选模式，不需要推进游戏 |
| 3 | `Esc` 检查 | 本地模式退出程序；联机模式 `NetLeaveToMenu` 回菜单 |
| 4 | `NetPoll()` | 联机时收发网络数据、推进握手/大厅/断线状态机（见第 9 节） |
| 5 | 固定 60Hz 累加器推进 0~8 个 tick | 见下 |
| 6 | `RenderFrame(hdc)` | 画到内存位图 → 一次性贴屏，只读状态 |
| 7 | `Sleep(1)` | 让出 CPU，不睡会把一个核心跑满 100% |

第 5 步的"固定 60Hz 累加器"是主循环的核心变化：

```c
dt = 真实耗时（夹到 0.25s）;  accumulator += dt;
while (accumulator >= SIM_DT /* = 1/60 */ && steps < 8) {
    本地模式 → UpdateGame(SIM_DT);
    主机    → UpdateHostGame(SIM_DT);
    客户端  → UpdateClientInput(SIM_DT);
    accumulator -= SIM_DT;
}
```

真实帧率可能是 59、144 或者偶尔卡一下，但**游戏逻辑永远按 1/60 秒一格地走**。
这一点对联机尤其重要：主机的 tick 数（`g_net.tick`）是双方共同的时间轴，
客户端发输入、主机发快照都挂在它上面，帧率忽高忽低没法这样对账。

逻辑推进（`SimulateTick`，本地和主机共用）内部又是固定顺序：

```
闪光/激光淡出计时 → [已结束? 只等 R 键 : ]
              ↓
         整局倒计时 g_timeLeft -= dt  ← 归零就 EndRound(1) 比分数
              ↓
         ControlTank(P1)   ← 扣冷却/护盾、开火、放雷/砌砖、移动
         ControlTank(P2)
              ↓
         UpdateBullets(dt)  ← 推进每一发子弹、判墙、判坦克
         UpdateMissiles(dt) ← 瞄准倒计时 / 穿墙飞行 / 爆炸
         UpdateMines(dt)    ← 布防倒计时 / 敌人踩雷
         UpdateItems(dt)    ← 刷道具、超时消失、拾取结算
              ↓
         UpdateSparks(dt)   ← 粒子飞散
```

**先移动再算子弹**很重要：如果反过来，子弹会打"上一帧的坦克位置"，
高速移动时能看见明显的穿透感。

**先移动再刷道具也有讲究**：`UpdateItems` 放在最后，拾取判定用的就是这一帧
移动之后的坐标，走到球上立刻生效，不会有一帧延迟。

## 3. 碰撞地基：两个函数撑起一切

### 3.1 `TileIsWall(cx, cy)`

```c
if (cx < 0 || cy < 0 || cx >= MAP_W || cy >= MAP_H) return 1;   /* 越界视作墙 */
c = g_map[cy][cx];
return c == '#' || c == 'B';
```

知识点在最后一行：**砖墙 `'B'` 和钢墙 `'#'` 对"能不能通过"来说完全一样**。
差别只出现在子弹撞上去时（钢墙反弹、砖墙吸收），这个差别由 `BulletProbe` 负责，
不在这里。职责分开，所以打穿砖墙只需要把字符改成 `'.'`，其他代码一行都不用改。

### 3.2 `BoxHitsWall(x, y, half)`

这是全程序调用最频繁的函数。它回答的问题是：
"一个中心在 (x,y)、半边长为 half 的方块，有没有压到墙？"

```c
x0 = floorf((x - half) / TILE);            // 左边界落在第几列
x1 = floorf((x + half - 0.001f) / TILE);   // 右边界落在第几列
y0 = floorf((y - half) / TILE);
y1 = floorf((y + half - 0.001f) / TILE);
```

三个细节都是坑，值得单独说：

**① 为什么减 0.001**
假设坦克右边界正好在 x = 26.0（第一格和第二格的分界线）。
`floor(26.0/26) = 1`，会把右边那一格也算进来——那一格明明是空的，却判定撞墙。
减 0.001 后 `floor(25.999/26) = 0`，正确。
游戏里坦克位置是浮点数，贴墙滑行时几乎必然出现"正好等于分界线"的情况，
不减这个 0.001 就会看到坦克离墙 1 像素就卡住。

**② 为什么返回值和调用方无关**
坦克用 `half = TANK_HALF = 9`，子弹用 `half = BULLET_R = 3`，
同一个函数，只是方块大小不同。所以"子弹能不能穿墙"和"坦克能不能穿墙"
共用一份碰撞代码，不会出现两套逻辑对不上的情况。

**③ 越界为什么单独判**
因为 `floorf` 对负数会给出负的格子号，而 `g_map[-1][x]` 是越界访问，会读到垃圾甚至崩溃。
所以先判范围再查表。这也是"坦克出不了地图"的完整实现——不需要额外的边界代码。

### 3.3 `MoveTank`：为什么 X、Y 要分开

```c
if (dx != 0) { 试 X，能过才改 pos.x }
if (dy != 0) { 试 Y，能走才改 pos.y }
```

如果两轴一起判（`BoxHitsWall(x+dx, y+dy)`），那么斜着顶到墙时，
两个轴都会被判"撞墙"，坦克原地不动——手感上就是"粘在墙上"。

分开判之后：X 被挡则 X 不动、Y 照走。这就是"顶着墙也还能蹭过去"，不会卡死。
这个技巧叫**逐轴分离检测**，几乎所有 2D 平台游戏和俯视游戏都用它。

斜着开的时候更明显：以 45° 顶到一面竖墙，只有 X 被挡，Y 照样走，
表现就是沿墙滑行——这正好是玩家对"斜着蹭墙"的预期。

### 3.4 角度转向：为什么朝向要存成浮点数

老版本的 `dir` 只有 0/1/2/3 四个值，位移只能落在坐标轴上。改成任意角度后：

```c
float angle;      // 0 = 朝上，顺时针为正
// 方向向量
dx = sinf(angle);
dy = -cosf(angle);
```

`-cos` 是因为屏幕的 y 轴向下：角度 0 要指向 (0,-1)。

**1）目标角度怎么来**

每帧把按下的方向键合成一个向量，再换算成角度：

```c
if (up) vy--;  if (down) vy++;
if (left) vx--; if (right) vx++;
target = atan2f(vx, -vy);        // 0=上, π/2=右, ±π=下, -π/2=左
```

`atan2` 的第二参用 `-vy`，是为了让"上"对应 0 而不是 ±π/2。
`W` + `A` 同时按 → `(vx,vy) = (-1,-1)` → `target = -45°`，这就是斜向。

**2）角度差要折到 (-π, π]**

从 179° 转到 -179° 只差 2°，但如果直接相减会得到 -358°，
坦克会傻乎乎地绕一整圈。所以 `AngleDiff` 把差值折进 `(-π, π]`，
永远走"最近的那一边"。

**3）转向是渐进的**

```c
diff = clamp(AngleDiff(angle, target), ±TANK_TURN*dt);
angle += diff;
```

`TANK_TURN = 8 rad/s`，一帧（1/60s）最多转 7.6°，转 90° 需要约 0.2 秒。
这段时间里玩家能看见车体在打方向，而不是贴图"啪"一下换了朝向。

**4）边走边转**

```c
align = cosf(AngleDiff(angle, target));   // 1 = 正对目标, 0 = 差 90°
speed = TANK_SPEED * align;
```

正对目标时全速；差 90° 时速度为 0（等于原地打方向）；45° 时是 70% 速度。
所以按住 `W`+`A`，坦克会先斜过来再加速，而不是"斜着平移"——
移动方向**永远是车头方向**，这是坦克和"八方向射击游戏"的根本区别。

**5）旋转怎么画**

没有去改 GDI 的世界变换（`SetWorldTransform` 对某些绘图函数不生效，
容易踩坑），而是把每个零件都在**车体坐标系**里描述一次：

```c
// f = 沿车头方向的距离，l = 向车身右侧的距离
OrientedPoint(&p, cx, cy, angle, f, l);
  → x = cx + sin(a)*f + cos(a)*l
    y = cy - cos(a)*f + sin(a)*l
```

车体用八角形（四角切 3px），履带是两条有向矩形，炮管是有向矩形 +
更亮的炮口点，炮塔是圆（圆旋转后还是圆，不用管角度）。
这样不管车头朝哪，画出的一定是同一个"俯视坦克"。

同样的思路也用于**开火**：子弹速度 = `AngleDir(angle) * BULLET_SPEED`，
所以炮管指哪打哪。激光更是完全按这个方向一步步推进（见 6.2）。

## 4. 子弹：逐行拆解（重点）

### 4.1 数据结构

```c
typedef struct {
    Vec2  pos, vel;   // 位置、速度（像素/秒）
    int   active;     // 池子里这一格是否在用
    int   owner;      // 0=P1 1=P2，只用于"出膛保护"判定
    int   bounces;    // 已反弹次数
    float life;       // 剩余寿命
    float grace;      // 出膛保护剩余时间
} Bullet;
```

只有 7 个字段，但每个都有存在的理由：

- `active` 而不是"用链表增删"：避免每帧 malloc/free，也不会有迭代器失效问题。
  遍历 64 个格子判断 `active` 的成本，比维护链表还低。
- `owner` 现在**不用于计分也不用于免疫**（计分只看谁死了），只用于判断 `grace` 该保护谁。
- `grace` 是本项目特有的补丁，见 4.2。

### 4.2 `Fire`：子弹从哪儿出生

```c
b->grace = 0.08f;
AngleDir(t->angle, &dx, &dy);
b->pos.x = t->pos.x + dx * (TANK_HALF + 3.0f);   // 9+3 = 12
b->vel.x = dx * BULLET_SPEED;                    // 斜着开炮 → 速度也是斜的
```

出生点在炮口外 12px。为什么正好是 12？因为命中判定的阈值就是
`TANK_HALF + BULLET_R = 9 + 3 = 12`。**子弹一出生就刚好卡在判定边界上**。

这带来两个后果：

1. 如果不做任何处理，每次开火都会瞬间自伤（打中自己）。
2. 更早的版本把出生点推到 15px 来避开，结果贴墙开炮时子弹直接生成在墙体内，
   被 `BulletProbe` 判成撞墙，子弹凭空消失。

最终方案：出生点回到 12（保证不会生在墙里），同时给 0.08 秒的 `grace`。
0.08 秒 ≈ 60fps 下 5 帧，子弹早已飞离车体（300px/s × 0.08 = 24px），
但仍在 5 次反弹的预算内，所以**弹回来的子弹照样能打到自己**。

`Fire` 里还有两道闸：冷却 0.34 秒、本人场上最多 3 发。后者防止玩家对着墙角狂点
攒出一墙子弹，把反弹变成"弹幕"。

### 4.3 `BulletProbe(nx, ny)`：一个函数，三种结局

```c
0 = 畅通      1 = 撞砖墙（已扣血，子弹该消失）      2 = 撞钢墙/边界（该反弹）
```

注意它**有副作用**：撞到砖墙时会直接调用 `DamageBrick` 扣血。
看起来不太"纯"，但这样调用方不需要知道撞的是哪一格，传个坐标就完事。
如果改成"返回撞到的格子号、由调用方扣血"，代码会多出 4 行样板，收益为零。

为什么不在这里直接做反弹？因为它不知道这次移动的方向——它只知道"目标点是墙"。
反射需要方向信息，而调用方才有。所以职责划分是：
**Probe 负责判断撞了什么，UpdateBullets 负责决定怎么反应。**

返回值 2 同时覆盖"钢墙"和"出界"，因为两者反应完全一样：反射。

### 4.4 `UpdateBullets`：三层结构

```c
for 每一发 active 的子弹:
    寿命倒计时；grace 倒计时
        ↓
    steps = 300 * dt / 3 + 1        // 按 3px 一刀切
    stepx = vel.x * dt / steps      // 每步位移
        ↓
    for 每一步:
        X 方向探测 → 砖墙? 消失 / 钢墙? 翻 vel.x / 畅通? 前进
        Y 方向探测 → 同上，翻 vel.y
        BulletHitCheck()            // 查有没有打中坦克
```

#### 第一层：为什么必须切子步

先算个数：60fps 时 `dt ≈ 0.0167`，子弹 `300px/s`，所以
**一帧位移 = 5px**。一格墙宽 24px，看起来"5px 不会穿过去"。

但问题不在墙的厚度，而在**检测时机**。假设子弹这一帧在墙前 1px，
下一帧的位置是 +5px，也就是墙内 4px。如果每帧只在"帧末"检测一次，
那么帧末它已经在墙里了 —— 检测到墙时它已经进去了，再反弹位置就是错的。
更糟的是贴着薄墙（比如转角处只有 24px 宽）时，两帧就能完全跨过去。

切成子步后，每一小步只有 2.5px（60fps），每步都检测，就不存在"跨过去"。
`+/3.0f` 是"每步最多 3px"的硬约束，`+1` 保证至少走一步（防止 dt 极小时 steps=0 导致除零）。

> 如果以后把 `BULLET_SPEED` 提到 900，`steps` 会自动变成 6，**不用改这里**。
> 这就是把"每步最大位移"写成常量而不是"固定切 3 份"的好处。

#### 第二层：为什么 X、Y 分开判

这是镜面反射的定义问题。想象子弹朝右上飞（`vel = (200, -200)`），
撞到一面**竖直的墙**（墙在右边）。正确反应是 `vel.x` 取反，`vel.y` 不变，
结果是朝左上飞 —— 像台球撞库边一样。

如果 X、Y 合并成一个点一起判，你只知道"下一个位置是墙"，不知道是撞了墙的
左面（该翻 x）还是下面（该翻 y）。分开判之后，信息天然就有了：
**X 方向被挡 = 撞的是竖直面 = 翻 vel.x**。

还有一个隐藏好处：**撞内角时两个轴都翻，子弹原路返回**。
在迷宫的直角角落里，一进一出正好 180°，这是最符合直觉的行为。

#### 第三层：`stepx = -stepx` 这一行干什么

```c
b->vel.x = -b->vel.x;   // 速度反转（影响下一帧）
stepx = -stepx;         // 这一步的位移也反转（影响这一帧剩下的步）
```

只翻 `vel.x` 是不够的：`stepx` 是循环外算好的局部变量，
这一帧剩下的几步仍然会按原来的方向推进，子弹会**穿进墙里**再下一帧才出来。
所以两个都要翻——这是很多手写碰撞里最容易漏的一行。

#### 反弹计数

```c
b->bounces++;
if (b->bounces > MAX_BOUNCE) { b->active = 0; break; }
```

`MAX_BOUNCE = 5`，判断用的是 `>` 所以实际能弹 **5 次**，第 6 次撞墙时销毁。
没有这个上限，子弹会在两个平行墙面之间永远弹下去，直到 9 秒寿命到期——
在狭窄走廊里会变成满屏乱飞的流弹，体验很差。

### 4.5 `BulletHitCheck`：为什么每步都查

```c
for (j = 0; j < 2; j++) {
    if (!alive) continue;
    if (shield > 0) continue;
    if (j == owner && grace > 0) continue;   // 只对"自己"生效的豁免
    if (|dx| <= 12 && |dy| <= 12) { 扣血... }
}
```

它被放在**子步循环内部**，而不是每帧调一次。原因和上面一样：
子弹一帧走 5px，坦克碰撞盒 18px，一帧一查其实也够；但子弹飞行中如果
恰好掠过坦克边缘，每步查能更精确地判定"擦到"，不会出现"明明碰到了却没掉血"。

判定用的是矩形（AABB）而不是圆：`|dx| <= 9+3 && |dy| <= 9+3`。
子弹是 6px 的小圆，坦克是 18px 的圆角方，用矩形近似最多差 2~3px，
在 24px 的格子里肉眼完全看不出来。如果用圆判，就要开根号，每帧几百次没必要。

`self` / 分数已经没有关系了：`HurtTank` 只看"谁死了"，死人给对方 +1。
所以这张表现在是这样的：

| 情况 | 掉血 | 加分 | 结束比赛 |
|---|---|---|---|
| 打中对手 | 是 | 死者是对手 → 自己 +1（若致死） | 是（若致死） |
| 打中自己 | 是 | 死者是自己 → **对手 +1**（若致死） | 是（若致死） |

也就是说："自己作死，对手收分"。这样就不存在"自杀不影响胜负"的漏洞了 ——
反正死了就要丢分，谁开的枪不重要。

### 4.6 把整条链路串起来（一次开火 → 一次自伤）

```
按 J
 └─ ControlTank: fire && !prevFire  → Fire()
      ├─ 冷却/数量检查
      ├─ 生成子弹，pos 在炮口 12px，grace = 0.08
      └─ AddSpark 炮口火光
 └─ UpdateBullets 每帧
      ├─ 子步推进，撞钢墙就翻速度分量，bounces++
      ├─ 撞到自己的车：grace 还 >0 ? 忽略 : 掉 1 血
      └─ bounces > 5 或 life <= 0 → active = 0
 └─ 打中时 BulletHitCheck: HurtTank → hp--，flash=0.12，溅 8 个火花
      └─ hp <= 0: alive=0, respawn=1.2s, 对手 score++（可能触发 EndRound）
 └─ DrawTank: 画白闪 / 护盾圈 / 车顶血条
```

## 5. 绿色砖墙（4 点血）的完整链路

改动分散在 6 个地方，缺一个就会出 bug：

| 环节 | 位置 | 做什么 |
|---|---|---|
| 数据 | `g_mapInit` 里的 `'B'` | 地图上有哪些砖 |
| 血量 | `g_brickHp[22][31]` | 每格剩几点血，`LoadMap` 初始化 |
| 阻挡 | `TileIsWall` | 砖墙算墙（坦克过不去） |
| 命中 | `BulletProbe` | 返回 1，并调用 `DamageBrick` |
| 销毁 | `DamageBrick` | 血量归零 → `g_map[cy][cx] = '.'` |
| 表现 | `DrawBrickTile` | 越暗 + 裂纹越多 |

蓝色道具砌出来的砖走的是**同一条链路**：`PlaceBrick` 只是往 `g_map` 里写了
一个 `'B'` 并把 `g_brickHp` 设成满血，之后它和地图自带的砖没有任何区别 ——
子弹照样 4 发打穿，坦克照样过不去，`DrawBrickTile` 照样按血量画裂纹。

关键设计：**打穿只是"把字符改回 `.`"**。改完之后：
`TileIsWall` 自动不再阻挡、`DrawArena` 自动改画地板、`BulletProbe` 自动不再命中。
不需要任何 `isDestroyed` 标志，也不需要从数组里删除元素。

这就是用"字符网格"当地图数据的好处——状态和表现天然一致，不会出现
"视觉上没了但还能挡子弹"这类经典 bug。

重开时 `ResetGame → LoadMap` 会把整张地图从模板重拷一遍，砖墙全部满血。
因为模板是 `const` 的，永远不会被污染。

## 6. 道具与四种特殊武器

道具系统只有一句话：**球被坦克碰到 → 写进坦克的几个计数器**。
真正复杂的是四种武器各自的实体，它们谁都不复用子弹，因为规则差得太远。

### 6.1 持有规则：四个计数器

一辆坦克手里能拿什么，全在四个字段里：

```c
int weapon;   /* 当前武器：普通 / 激光 / 追踪 */
int ammo;     /* 特殊武器还能打几次 */
int mines;    /* 存着的地雷 0~2 */
int bricks;   /* 存着的砖块 0~2 */
```

`PickItem` 是唯一往这四个字段里写东西的地方（除了阵亡清零），返回 1 / 0 表示"收下 / 收不下"：

| 类型 | 收下时做什么 | 收不下时 |
|---|---|---|
| 🔴 红 | `weapon = 激光; ammo = 3` | — |
| 🟢 绿 | `weapon = 追踪; ammo = 3` | — |
| 🟡 黄 | `mines++` | `mines` 已经是 2 就不收 |
| 🔵 蓝 | `bricks++` | `bricks` 已经是 2 就不收 |

三条规则就是靠这张表落地的：

1. **一件道具只能 3 次** —— 写的是 `ammo = 3` 而不是 `ammo += 3`。
   所以不存在"攒 6 发激光"，每次拾取都是"换一把新的、给满 3 次"。
2. **新道具顶掉旧道具** —— 红绿写的是同一个 `weapon` 字段，后写的直接覆盖前一个，
   旧武器剩下的次数一个字都不保留。这就是"能换枪、但不能同时带两把"的最简实现。
3. **黄蓝不被顶掉、各存 2 个** —— 它们是独立字段，红绿根本不碰。
   收不下时 `PickItem` 返回 0，`UpdateItems` 里直接 `break` 而不销毁小球，
   所以球还留在地上，等你有空位再来捡 —— 不会出现"捡了个白捡"。

**阵亡清空**就是 `HurtTank` 阵亡分支里的四行赋值：

```c
t->weapon = WPN_NORMAL;
t->ammo   = 0;
t->mines  = 0;
t->bricks = 0;
```

放在 `HurtTank` 里而不是重生分支里，是因为"阵亡"只有这一个入口 ——
被子弹、激光、追踪弹、地雷打死，或者自己把自己搞死，都必然经过这里，清一次就够，
不用在每个伤害来源上各补一遍。

### 6.2 一个统一的入口 `HurtTank`

在加道具之前，"掉血"这件事散在 `BulletHitCheck` 里。四种子弹/爆炸都来一遍会重复四次，
所以抽了一个函数：

```c
static void HurtTank(int idx, int dmg, float hx, float hy)
```

- **不需要"凶手"参数**：计分只看谁死了 —— `g_tanks[1 - idx].score++`。
  自己把自己弄死，分数照样给对手，规则上没有任何"自杀免责"的漏洞
- 计分规则只在这里实现一次：**阵亡才 +1 分**，打中不掉分
- 分数到 36 时在这里调 `EndRound(0)`

`BulletHitCheck` 因此缩成了十几行：判定重叠 → 扣子弹 → 调 `HurtTank`。

### 6.3 红 · 折射激光炮（`CastLaser`）

激光不是"慢慢飞的实体"，而是**一次性光路计算**：

```c
AngleDir(t->angle, &d.x, &d.y);          // 任意角度出发
p = 炮口位置（车头方向 16px，若在墙里就往回收）

while (left > 0) {
    if (fabs(d.x) > 1e-4) {
        nx = p.x + d.x * 3;
        h = LaserAt(nx, p.y);            // 0 空 / 1 砖 / 2 钢
        if (h == 1) { 砖掉血; break; }    // 砖墙吸收
        if (h == 2) d.x = -d.x;          // 竖面：只翻 x
        else        p.x = nx;
    }
    if (fabs(d.y) > 1e-4) { 同理处理 y }

    if (bounced) { 记折点; if (++bounces > LASER_BOUNCE) break; }
    left -= 3; traveled += 3;
    每个目标只结算一次伤害;
}
```

和子弹的区别只有三点：

1. **步长固定 3px，没有速度概念** —— 它是瞬时命中，所以要走多快都无所谓，
   只要保证每步足够小、不会跨过 24px 的墙。
2. **路程按"总长"扣减**，而不是按时间 —— `LASER_RANGE = 620` 就是"最远折射距离"。
   折射不额外计费，所以折 3 次会把 620px 分摊到 4 段上。
3. **撞砖墙就终止**，因为砖会吸光；钢墙才反射。

X、Y 分开推进还有额外的好处：**斜射时反射自动就是对的**。
斜着打到一面竖墙，只有 x 分量翻号，y 继续走，出来就是镜面反射；
打到内角时两个分量都翻，原路返回。不需要算入射角、不需要向量法线。

伤害统一 2 点，打到敌人和自己一样。另外 `traveled > 30` 之前不判定自己 ——
否则光束一出生就贴在自己脸上，等于每炮自残。

光轨只在 `Laser` 里存折点，`DrawLaser` 拿折点画三层线，0.3 秒淡出。
所以"光"本身是瞬时生效的，屏幕上的线只是残影。

### 6.4 绿 · 追踪弹（`UpdateMissiles`）

这是唯一一个**有生命周期的两阶段实体**：

| 阶段 | `phase` | 做什么 | 为什么 |
|---|---|---|---|
| 瞄准 | 0 | 每帧把 `lockPos` 更新成敌人当前位置，并画收缩的准星 | 敌人看得见，才有时间跑 |
| 飞行 | 1 | 锁定点冻结，朝它转弯飞过去，**完全不判墙** | 穿墙 + 打固定点，跑开就能躲 |

关键的一行在瞄准倒计时归零时：

```c
m->lockPos = 敌人的当前位置;   // 冻结
m->phase = 1;
```

从这里开始 `lockPos` 不再变。敌人只要在"发射瞬间 + 飞行时间"之内离开那个点，
爆炸半径 30 就罩不到他 —— 这就是"瞄准时间给敌人躲避"的实现方式。

飞行时用 `MISSILE_TURN = 0.22` 做插值转向：

```c
m->vel += (期望速度 - m->vel) * 0.22;
```

不是瞬间对准，所以它会画出一条弧线。这个系数就是"追踪的笨拙程度"：
调小更像炮弹（好躲），调大更像追踪导弹（难躲）。

**不判墙**这件事没有任何黑科技 —— 飞行分支里根本没有调用 `BoxHitsWall` 或
`TileIsWall`，坐标想怎么走就怎么走。所以子弹穿墙不是"特判"，而是"没写碰撞"。

### 6.5 黄 · 地雷（`PlaceMine` / `UpdateMines`）

- **存 → 埋**：拾到黄色球只是 `mines++`（最多 2 个），**埋在哪儿由玩家自己决定**：
  把车开到想埋的位置，按放置键（P1 是 `空格`，P2 是小键盘 `1`），就地埋一颗并 `mines--`。
  同一个位置 10px 以内已经有一颗雷时会拒绝（`PlaceMine` 开头那个循环），
  免得连按两下把两个存货埋成一个点。
- **显型 → 隐形**：`blink = 0.9` 秒。`DrawMines` 在前 0.35 秒按 100% 不透明度画
  （黄圈 + 雷体 + 四根刺），接着 0.55 秒淡出，之后 `blink <= 0` 直接 `continue`，
  屏幕上再也看不到它 —— 不用做视野遮挡、不用分玩家渲染，这就是"隐形"。
- **触发**：用"走进来"判定，而不是"在圈里"判定：

```c
mask  = 这一帧站在触发圈里的车（位掩码）
enter = mask & ~m->inside;      // 刚刚走进来的
m->inside = mask;
if (!enter) continue;           // 一直站在里面不算
```

  这样处理了两件事：
  1. 布防结束时自己还站在雷上，不会被自己炸（他"本来就在里面"）。
  2. 但只要走开再走回来，`enter` 就会置位 —— **自己的雷照样炸自己**，
     符合"伤害不分敌我"。想退回旧规则，把 `MINE_FRIENDLY` 改成 0 即可。

- **爆炸**：半径 26px 内所有车都吃 2 点伤害，不区分是谁埋的。
  如果两颗雷同时炸死两人，就是各得 1 分。

地雷有 45 秒寿命，到期自动消失，避免整张图被埋满。

### 6.6 蓝 · 砖块（`PlaceBrick`）

砌砖看着最简单，其实有两个坑，都跟"24px 的格子里塞 18px 的车"这个尺寸有关。

**坑一：砌在脚下会把自己钉死。**
砖是实心的，如果直接砌在车所在那一格，那么之后**任何方向**的新位置都还压着这格墙，
`MoveTank` 里的 `BoxHitsWall` 永远返回 1 —— 车彻底动不了，连开炮都只能打自己脚下那块砖。
所以 `BrickTargetCell` 取的是**车头前一格**：车体所在格，沿朝向的主方向推一格
（斜着开的时候取更大的那个分量，保证只推一格）。

**坑二：车几乎总在跨界。**
车中心落在第 k 格，不等于车体只在第 k 格里 —— 中心离格子边界小于 9px 时，车头已经探进第 k±1 格，
而"前一格"正好就是这个 k±1 格。于是砖一出现，可能有小半个车头正好在砖里，又回到坑一。

`PushOutOfBrick` 就是补这个洞的：

```
车中心在第 k 格、砖在第 k+1 格  →  车头最多压进去 9px
往回退：第 k 格本身是空地，退到 9px 以内必然完全脱离
预算给到 12px，一定够用
```

- 只沿**主方向**退（`fabs(dx) >= fabs(dy)` 时只动 x），不斜着退，避免被挤到侧墙上；
- 每退 1px 都重新判一次 `BoxHitsWall` 和 `HitsOtherTank`，所以退的过程本身不会穿墙；
- 万一真退不出去（背后是墙、旁边还有对手），就把刚写进去的 `'B'` **撤掉**、**不扣存货** ——
  宁可"按了没反应"，也不能把玩家埋进墙里。

还有个边界情况：对手可以在你死后往你的出生点上砌砖（那时没有车站在那儿，判定不会拦）。
所以 `ControlTank` 的重生分支里多了一句：出生格如果是 `'B'`，先凿开再放车。
不然一复活就整个卡在墙里，那局基本就废了。

放置前 `DrawPlaceHint` 会把目标格画成一个虚线方框（放不下时变红），
所以上面这些"为什么没反应"的情况，玩家提前就能看见。

### 6.7 道具刷新（`SpawnItem`）

```c
for (tries = 0; tries < 60; tries++) {
    gx = rand() % MAP_W;  gy = rand() % MAP_H;
    if (g_map[gy][gx] != '.') continue;                    // 必须是地面
    if (离任意坦克 < 56px) continue;                        // 不能贴脸
    放球; return;
}
```

用"随机试 60 次"而不是"收集所有合法格子再随机挑一个"，是因为地图上地面格有 200 多个，
随机命中率很高（432 格地面 / 682 格），试 60 次几乎不可能全失败，代码却只有五行。
真失败了就这一轮不刷，6~10 秒后自然还会再试 —— 不需要处理失败分支。

## 7. 绘制层

### 6.1 双缓冲

```c
if (!g_memDC) { 创建内存 DC + 同尺寸位图 }
Render(g_memDC);                       // 全画在内存里
BitBlt(target, ..., g_memDC, ...);     // 一次性贴到窗口
```

不这么做的话，每帧会看见"背景刷白 → 画墙 → 画坦克"的过程，也就是**闪烁**。
内存 DC 只创建一次，之后每帧复用——这是 GDI 游戏的标准写法。

### 6.2 绘制顺序 = 图层顺序

`Render` 里 8 个调用就是 8 个图层，后面盖住前面：

```
背景 < 场地 < 地雷 < 道具 < 粒子 < 子弹 < 重生标记 < 坦克 < 激光 < 追踪弹 < HUD < 结算面板
```

想让子弹压在坦克上面（比如表现"子弹从车顶飞过"），把 `DrawBullets` 挪到
`DrawTank` 后面即可，一行都不用改。这种"顺序表"式渲染比维护 z-index 直观得多。

### 6.3 GDI 句柄纪律

源码里每一处都是这个模式：

```c
br = CreateSolidBrush(color);          // 建
ob = SelectObject(dc, br);             // 选进 DC，记住旧对象
...Ellipse / RoundRect / FillRect...   // 画
SelectObject(dc, ob);                  // 还原（必须先还原）
DeleteObject(br);                      // 再删
```

三条铁律：

1. **建了必须删**，否则句柄泄漏。GDI 每进程上限 10000 个，跑几分钟就会画不出来。
2. **删除前必须先选出 DC**，否则删的是"正被使用的对象"，会失败。
3. **必须还原旧对象**，否则那个旧对象永远处于"被选中"状态，删不掉。

`DrawTank` 一次调用要建删 5~6 个对象，60fps 下每秒几百次——
看起来开销大，但 GDI 创建纯色画刷/画笔是内存操作，实测毫无压力。

## 8. 主循环为什么这么写

```c
while (PeekMessageW(&msg, NULL, 0, 0, PM_REMOVE)) { ... }   // 抽干消息
...
if (g_appMode == APP_MENU) { Sleep(10); continue; }          // 菜单模式空转
if (KeyDown(VK_ESCAPE)) { 本地退出 / 联机 NetLeaveToMenu(); }
NetPoll();                                                    // 网络轮询（联机模式）
dt = QPC 求差，夹到 0.25s;  accumulator += dt;
while (accumulator >= SIM_DT && steps < NET_MAX_TICK_CATCHUP /* 8 */)
    { 按模式推一个固定 tick; accumulator -= SIM_DT; }
RenderFrame(hdc);  Sleep(1);
```

**为什么是 `PeekMessage` 而不是 `GetMessage`？**
`GetMessage` 在没消息时会阻塞挂起，而游戏需要"没消息也要继续跑"。
`PeekMessage` 只取不阻塞，取完就往下走。

**为什么要固定 60Hz（累加器），而不是"算出多少 dt 就推多少"？**
老版本是 `dt` 直接喂给 `UpdateGame`，帧率波动时坦克和子弹的速度会轻微忽快忽慢。
改成固定 tick 有两个动机：
1. **确定性**。同样 1/60 秒的输入 → 同样的位移，主机和单机不会因为刷新率不同而行为漂移。
2. **联机对账**。主机的 `g_net.tick` 是协议里的回合内时间戳（快照、输入确认都引用它），
   tick 的步长必须是恒定的，客户端才能判断"这份快照比我现在的新还是旧"。

**为什么夹 `dt` 到 0.25s、并且一轮最多追 8 个 tick？**
拖动窗口标题栏时，Windows 会进入"窗口移动模态循环"，主循环被卡住，
松手后 `dt` 可能是 2 秒。两个保险配合工作：

- `dt` 夹到 0.25s：卡顿 2 秒最多只往累加器里塞 0.25 秒"欠账"；
- 每轮最多追 `NET_MAX_TICK_CATCHUP = 8` 个 tick：追不完的直接把 `accumulator` 清零丢弃。

效果是"卡顿期间游戏变慢"，而不是"松手后连环快进 120 帧"——
尤其联机时快进 120 个 tick 意味着一次发出 120 份快照，会瞬间挤爆发送缓冲。

**为什么用 `QueryPerformanceCounter`？**
`GetTickCount` 精度只有 15.6ms，比一帧（16.7ms）还粗，算出来的 dt 会忽大忽小，
表现为画面轻微抖动。QPC 是微秒级，够用。

**为什么 `SetProcessDPIAware()`？**
不调用的话，Windows 在 150% 缩放的屏幕上会把整个窗口按位图拉伸，
768px 的画面变成 1152px 的模糊画面。声明 DPI 感知后由我们自己控制像素，
画面锐利（代价是窗口在高分屏上物理尺寸偏小，但对固定尺寸的游戏正合适）。

**菜单模式为什么 `Sleep(10)` 而不是继续 60Hz？**
模式选择窗口是系统按钮/输入框，自己不画任何东西，主窗口还隐藏着。
空转省电，同时 `prev/accumulator` 也要重置——选完模式进入游戏时，
第一帧的 dt 不能把"玩家在菜单里发呆的两分钟"算进来。

## 9. 局域网联机：主机权威 + 全量快照

联机部分的总体思路一句话：**只有主机跑游戏逻辑，客户端只上报按键、照着主机画面渲染**。
没有客户端预测、没有插值、没有 UDP——局域网内延迟就一两毫秒，这些都不值得做。
付出的代价是客户端的操作手感带半个来回的延迟，在可信局域网里察觉不到。

### 9.1 AppMode / NetPhase：两层状态机

```c
AppMode  = APP_MENU / APP_LOCAL / APP_HOST / APP_CLIENT   /* 程序在哪个模式下 */
NetPhase = NET_NONE / NET_WAIT_PEER / NET_CONNECTING / NET_HANDSHAKE /
           NET_LOBBY / NET_RUNNING / NET_DISCONNECTED      /* 联机走到哪一步了 */
```

`g_appMode` 决定主循环每帧推什么（`UpdateGame` / `UpdateHostGame` / `UpdateClientInput`），
`g_netPhase` 是联机内部更细的阶段。分成两层而不是一个大枚举，是因为
"我是主机还是客户端"和"我连到哪一步了"是两个独立的问题——
同一个 `NET_LOBBY` 阶段，主机和客户端要做的事完全不同。

### 9.2 启动菜单窗口（`CreateMenuWindow`）

程序不再一启动就进游戏：`WinMain` 先创建主窗口（隐藏），再弹一个独立的
模式选择窗口，四个按钮：本地双人 / 创建房间 / 加入房间 / 退出；
"创建房间"页只有一个端口输入框（预填 27515），"加入房间"页有三个输入框：
主机 IP、端口、6 位邀请码。

选完之后销毁菜单窗口、显示主窗口。断线或联机退出时（`NetEnterDisconnected` /
`NetLeaveToMenu`）也是**回到这个菜单**：关 socket、隐藏主窗口、重新 `CreateMenuWindow`。
菜单是普通系统控件，所以主循环在 `APP_MENU` 下只 `Sleep(10)` 空转等按钮消息。

### 9.3 TCP 非阻塞收发与 20 字节帧头

socket 全部设成非阻塞（`ioctlsocket` + `FIONBIO`），并开 `TCP_NODELAY`
（禁用 Nagle，避免小消息凑包）。收发都不可能卡住主循环：

- **发**：所有消息先进 512KB 的 `tx` 静态队列（`NetQueueMessage`），
  每帧末尾 `NetFlush` 循环 `send`，碰上 `WSAEWOULDBLOCK`（对端暂时收不下）
  就留到下一帧继续发。**排队 + 尽力冲刷**，比"每个消息一次阻塞 send"更适合 60Hz 节奏。
- **收**：每帧 `recv` 循环灌进 64KB 的 `rx` 缓冲，直到 `WSAEWOULDBLOCK`；
  然后 `NetParseFrames` 把字节流按帧切开逐条处理。

TCP 是字节流，"一条消息"从哪里开始到哪里结束要自己定义，所以每帧前面有
**固定的 20 字节帧头**，全部按网络字节序（大端）打包：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | magic（4） | `"TBGP"`，一眼识别"这不是我们的数据"（比如连到了别的服务） |
| 4 | version（2） | 协议版本号，改协议后老客户端会被拒 |
| 6 | type（2） | 消息类型，见下表 |
| 8 | payload 长度（4） | `NetParseFrames` 靠它知道这一帧到哪结束；不完整就留着等下帧 |
| 12 | session（4） | 会话校验，见 9.5 |
| 16 | round（4） | 回合校验，见 9.5 |

字段编码不用结构体直接 `memcpy`（结构体有对齐填充、字节序也不可控），
而是 `NetWriter` / `NetReader` 一层层包：`NW_U8/U16/U32/F32` 写、`NR_*` 读，
`htons/htonl` 统一转网络字节序，越界自动置 `ok = 0`。解码侧每个字段都做范围检查。

### 9.4 消息类型一览

| 消息 | 方向 | 载荷 | 作用 |
|---|---|---|---|
| `HELLO` | 客户端→主机 | 4 字节邀请码 | 连上后报出邀请码，请求入座 |
| `WELCOME` | 主机→客户端 | 4 字节 session + 1 字节角色 | 邀请码正确：下发会话号，确认"你是蓝方 P2" |
| `ERROR` | 主机→客户端 | 1 字节原因码 | 邀请码错误 / 房间已有人，拒绝后关连接 |
| `READY` | 客户端→主机 | 1 字节 | 客户端"我按了 R 准备好了"；主机自己的准备状态由 `LOBBY` 广播 |
| `LOBBY` | 主机→客户端 | 双方准备状态各 1 字节 | 每 100ms 广播一次，让客户端看到主机的准备进度 |
| `START` | 主机→客户端 | 空 | 双方都准备后正式开始新回合 |
| `INPUT` | 客户端→主机 | seq + held + pressed（各 4 字节） | 客户端每 tick 上报按键 |
| `SNAPSHOT` | 主机→客户端 | 全量快照（约几 KB） | 主机每 tick 广播整局状态 |
| `PING` / `PONG` | 双向 | 空 | 大厅里客户端每秒一次保活，双方都靠"5 秒没收到数据"判断超时 |
| `LEAVE` | 双向 | 空 | 正常退出时通知对方 |

握手流程：主机建房 → 客户端 TCP 连接 → 客户端发 `HELLO`（带邀请码）→
主机核对邀请码，不对就回 `ERROR` 并关连接（房间继续等下一个），对了就回 `WELCOME`
并关掉监听 socket（**房间只收一个玩家**，之后再来连接的一律拒绝）。

### 9.5 session / round：防止旧数据串场

- **session（会话号）**：主机建房时随机生成，随 `WELCOME` 发给客户端。
  此后双方发出的每条消息帧头都带它，收到不匹配的一律按"无效数据"断线——
  防止上一局残留的 TCP 数据被当成这一局的消息。
- **round（回合号）**：每次 `NetTryStartRound` 开始新回合时 `+1`。
  协议里唯一允许 round 前进的消息是 `START`（客户端据此确认"新回合开始了"），
  其他所有消息要求 `round == 当前值`，否则断线。这样**重赛时上一回合还在路上
  的旧快照、旧输入都会被拒绝**，不会混进新回合。

### 9.6 输入：held / pressed 与边沿锁存

键盘被压成 7 位掩码（`IN_UP`~`IN_BRICK`），一份输入拆成两个字段：

- `held`：这一 tick 按着哪些键（用于移动、转向——按住就生效）；
- `pressed`：这一 tick **新按下**哪些键（`keys & ~上一tick的keys`，用于开火、放雷、
  砌砖——只认边沿，按住不放也只触发一次）。

客户端每 tick 发一次 `INPUT(seq, held, pressed)`。主机收到后：

```c
if (seq <= g_net.remoteInputSeq) return;      /* 旧输入 / 重复包直接丢弃 */
g_net.remoteInputSeq = seq;
g_net.remoteHeld    = held;
g_net.remotePressed |= pressed;               /* 注意 |=，不是 = */
```

`remotePressed |= pressed` 就是**边沿锁存**：网络抖动时，可能两个 tick 的输入
在同一帧一起到达。如果写 `=`，前一个 tick 的"按下 J"就被覆盖丢了，表现为"偶尔按了没反应"；
`|=` 把所有"按下的瞬间"攒起来，交给模拟时消费掉（`UpdateHostGame` 用完清零）。
同时 seq 单调递增检查保证乱序/重复的输入不会倒灌。

### 9.7 主机权威模拟（`UpdateHostGame`）与客户端渲染（`UpdateClientInput`）

主机每个固定 tick 做四件事：

```c
in[0] = MakeInput(0, NetReadOnlineKeys());   /* P1：主机自己的键盘 */
in[1].held = g_net.remoteHeld;               /* P2：客户端上报的输入 */
in[1].pressed = g_net.remotePressed;  g_net.remotePressed = 0;
SimulateTick(in, dt);                        /* 和本地模式完全同一段模拟代码 */
g_net.tick++;
NetSendSnapshot();                           /* 打包全量状态发出去 */
```

`SimulateTick` 就是本地双人用的那份逻辑，一字不改——**联机没有第二套游戏规则**，
只是"读键盘"换成了"读远端输入"。这是整个联机设计里最省事的决定。

`EncodeSnapshot` 把**全部**状态打成一个平面字节流：地图、每格砖墙血量、
两辆坦克、所有子弹、激光轨迹、追踪弹、地雷、道具、粒子，一个不落。
"全量快照"意味着客户端不需要任何差量/补丁逻辑——收一份、验一份、覆盖一份，
解码失败（字段越界、长度不齐）就断线。局域网带宽不要钱，这是最不容易出 bug 的选择。

客户端恰恰相反，**完全不跑模拟**：

```c
/* UpdateClientInput：每 tick 只做一件事——上报输入 */
keys = NetReadOnlineKeys();
pressed = keys & ~g_prevKeys[1];  g_prevKeys[1] = keys;
NetSendInput(++g_net.inputSeq, keys, pressed);
```

画面完全来自 `SNAPSHOT`：`DecodeSnapshot`（全字段校验，失败断线）→ `ApplySnapshot`
（整块 memcpy 覆盖本地状态）→ `RenderFrame` 照常画。快照带 `tick` 时间戳，
客户端只接受**更新的**快照（`tick > lastSnapshotTick`），乱序到达也不会"画面倒带"。

### 9.8 断线清理（`NetEnterDisconnected`）

所有异常——对端正常退出（收到 `LEAVE`）、对端掉线（`recv` 返回 0）、
协议数据无效、快照校验失败、5 秒超时（`NET_TIMEOUT_MS`）、发送缓冲塞满——
都汇到同一个出口：关两个 socket、弹提示框、回到模式选择窗口。
**不做中途重连**：联机状态里存的输入序号、tick、准备状态全部作废最干净，
想再战就重新建房。程序退出时 `WinMain` 尽力补发一条 `LEAVE` 再清理 Winsock，
让对方能立刻收到"对方已退出"而不是干等 5 秒超时。

## 11. 调试技巧

**1. 自动演示模式**
编译时加 `/DAUTO_DEMO`，两辆车会自动巡逻对射，适合盯着看反弹、砖墙破坏和道具效果，
不用一边手忙脚乱一边观察：

```
cl /utf-8 /O2 /DAUTO_DEMO main.c user32.lib gdi32.lib ws2_32.lib
```

**2. 逻辑自动化测试**
本轮开发用了一个技巧：把 `main.c` 当"头文件"整个 include 进测试程序，
这样就能直接调用里面的 `static` 函数，在控制台里断言规则，不用开窗口点来点去：

```c
#define WinMain TankBattle_WinMain   /* 先改名，避免和测试的 main 冲突 */
#include "main.c"
#undef WinMain

Fire(&g_tanks[0], 0);                // 直接开炮
assert(g_lasers[0].npts >= 3);       // 检查是否发生折射
```

最新一轮验证了 47 项：地图连通性 / 无窄道、出生点可站、四种道具的拾取与上限、
新武器顶掉旧武器、阵亡清空、置雷位置与同处不叠、砌砖的目标格 / 4 血 / 顶出 / 拒绝条件……
另外还跑了一个 6 万帧的随机压力测试，专门盯"坦克永远不会卡进墙里"这条不变式。

**3. 离屏渲染测画面**
同一个思路还能测画面：建一个内存 DC，摆好场景后直接调 `Render(memDC)`，
`GetDIBits` 取像素存成 BMP。好处是**可以构造任何想要的状态**（激光正在折射、
准星正在收缩、结算面板），不用靠运气等它自己出现。

**4. 想确认"子弹真的在反弹"**
别靠眼睛看。在 `UpdateBullets` 里加一行 `printf("%.0f %.0f %.2f\n", b->pos.x, b->pos.y, b->vel.x);`，
重定向到文件后看轨迹：正常反弹应该出现"某个坐标开始反向"的拐点。
（本项目开发时就是这么验证的：y 从 556→378 上升，然后 396→422 反向。）

**5. 想确认砖墙是 4 血**
统计屏幕上绿色像素数量，每打一发数一次。第 1~3 发只是变暗（像素数微降），
第 4 发会骤降一大截（整块变地板）。

**6. 常见 bug 自查表**

| 现象 | 多半是 |
|---|---|
| 坦克穿墙 | `BoxHitsWall` 的 `-0.001f` 被删了；或速度 × dt > 半格宽 |
| 子弹穿墙 | `steps` 计算错（比如写成了固定 1） |
| 斜撞墙方向不对 | X、Y 没分开判，或漏了 `stepx = -stepx` |
| 贴墙开炮子弹消失 | `grace` 太小，或出生点被推进了墙里 |
| 激光不折射 | `LASER_BOUNCE` 为 0，或撞的是砖墙（砖墙是吸收，不反射） |
| 激光刚开炮就打自己 | `traveled <= 30` 的出膛保护被删了 |
| 追踪弹永远打中 | 检查飞行分支里是不是误加了 `BoxHitsWall` |
| 地雷刚放下就炸自己 | `MINE_ARM` 为 0，或触发判定漏了 `1 - owner` |
| 放雷 / 砌砖按了没反应 | 存货为 0；或目标格不是空地、被对方占着（看屏幕上的红色预览框） |
| 砌完砖自己动不了 | `PushOutOfBrick` 没调，或它的 12px 预算不够 |
| 道具刷在墙上/坦克脸上 | `SpawnItem` 里两条 `continue` 条件被删了 |
| 倒计时不走 / 到 0 不结算 | `g_timeLeft` 没减，或 `EndRound(1)` 没调 |
| 画面闪烁 | 没走内存 DC，直接画在窗口上 |
| 中文字变方块 | 编译没加 `/utf-8`，或源码存成了 GBK |
| 高分屏模糊 | 没调 `SetProcessDPIAware()` |
| 拖窗口后连环快进 / 瞬移 | `dt` 上限或 `NET_MAX_TICK_CATCHUP` 被调太大，或累加器没清零 |
| 对方一直连不上 | Windows 防火墙没放行"专用网络"；IP 抄错；两边端口不一致 |
| 邀请码总是不对 | 客户端把 `%06u` 的前导 0 弄丢了（必须输满 6 位） |
| 连上秒断 | 帧头 magic / 版本号被改过；两边的程序版本不同 |
| 客户端"按了没反应" | 输入的 `pressed` 边沿丢了（检查 `remotePressed |= pressed` 是不是写成了 `=`） |
| 客户端画面倒带 | 快照没按 `tick > lastSnapshotTick` 过滤旧包 |
| 重赛后状态错乱 | `round` 校验被删，上一回合的旧 SNAPSHOT / INPUT 混进了新回合 |

**7. 测联机断线不用真拔网线**

`main.c` 里留了一个 `g_netQuiet` 标志：测试程序把 `main.c` 整个 include 进去后
直接把它置 1，`NetEnterDisconnected` 就只改状态、不弹 MessageBox，
可以在控制台里把"对端退出、超时、协议错误、快照校验失败"这些分支挨个触发断言，
不用真开两个窗口、手动掐网线。
